## この章で分かるようになること

- SELECT を、書かれた順ではなく「実行される順」に読める
- `COUNT(*)` と `COUNT(列)`、`GROUP BY`、`DISTINCT`、`ORDER BY` と `LIMIT` が、結果の行や値をどう変えるかを説明できる
- エラーにならずに結果がずれる失敗を、**ズレの3分類**で言い分けられる
- **検算の4手順**で、Claude Code の結果を確かめられる

## 1. SELECT は「表から表を作る」

SELECT は、表を材料にして、新しい表（結果）を作る文です。書く順番と、PostgreSQL が考える順番が違うので、**考える順番で読む**のがコツです。

```sql
SELECT source_id, COUNT(*) AS article_count   -- ④ どの列を出すか
FROM articles                                  -- ① どの表から
WHERE status = 'active'                        -- ② どの行を残すか
GROUP BY source_id                             -- ③ どの単位でまとめるか
ORDER BY source_id;                            -- ⑤ どの順に並べるか
```

:::result 3
| source_id | article_count |
|---:|---:|
| 1 | 2 |
| 2 | 2 |
| <span class="null">NULL</span> | 1 |
:::

| 読む順 | 句 | やること | この例では |
|---|---|---|---|
| ① | `FROM` | 材料の表を決める | `articles` の5行 |
| ② | `WHERE` | 条件に合う行だけ残す | `status` が `active` の行（いまは5行とも） |
| ③ | `GROUP BY` | 同じ値の行を1つにまとめる | `source_id` ごとに3グループ |
| ④ | `SELECT` | 出す列を決める（数えるならここ） | グループごとの行数 |
| ⑤ | `ORDER BY` | 並べる | `source_id` の小さい順 |
| ⑥ | `LIMIT` | 先頭から何行だけ出すか | （この例では無し） |

> 🔍 **なぜ読む順が大事なのか**：結果の行数が変わるのは、①〜③と⑥のどこかです。行数がおかしいときは、`SELECT` の列ではなく、`FROM`・`WHERE`・`GROUP BY`・`LIMIT` を順に疑います。

## 2. WHERE：行を残す条件

`WHERE` は、条件が「正しい」行だけを残します。

```sql
SELECT id, title, published_at
FROM articles
WHERE published_at >= '2026-10-02 00:00+09'
ORDER BY id;
```

:::result 3
| id | title | published_at |
|---:|---|---|
| 2 | 社内AIの導入率が過半数に | 2026-10-02 08:30:00+09 |
| 3 | 半導体工場の新設計画を発表 | 2026-10-02 12:00:00+09 |
| 5 | 配信元不明の転載記事 | 2026-10-03 18:00:00+09 |
:::

記事4（公開日時が [[NULL]]）は、結果に入っていません。公開日時が分からないので、「10月2日以降か」と聞かれても「正しい」とは言えないからです。

> 🔍 **NULL の行は、WHERE で静かに消える**：「10月2日以降**ではない**記事」を `WHERE published_at < '2026-10-02 00:00+09'` で探しても、記事4は出てきません。どちらの条件でも消えるので、2つの結果を足しても全体の5件になりません。理由（NULL の三値論理）は第9章で扱います。いまは「NULL を許す列で絞ったら、NULL の行の行き先を確かめる」と覚えてください。

## 3. 数える：COUNT(*) と COUNT(列)

`COUNT` には2つの書き方があり、数えるものが違います。

```sql
SELECT COUNT(*)                  AS all_rows,
       COUNT(published_at)       AS with_published_at,
       COUNT(source_id)          AS with_source,
       COUNT(DISTINCT source_id) AS sources_used
FROM articles;
```

:::result 1
| all_rows | with_published_at | with_source | sources_used |
|---:|---:|---:|---:|
| 5 | 4 | 4 | 2 |
:::

| 書き方 | 数えるもの | 結果 |
|---|---|---:|
| `COUNT(*)` | 行の数 | 5 |
| `COUNT(published_at)` | `published_at` が NULL でない行の数 | 4（記事4を数えない） |
| `COUNT(source_id)` | `source_id` が NULL でない行の数 | 4（記事5を数えない） |
| `COUNT(DISTINCT source_id)` | NULL を除いた、`source_id` の種類の数 | 2（1 と 2） |

「記事は何件？」と頼んで返ってくる数字は、どれも「記事の件数」に見えます。どの `COUNT` かで答えが変わるので、SQL の `COUNT(...)` の中を必ず読みます。

## 4. GROUP BY：まとめて数える

第1節の例の `GROUP BY source_id` は、「`source_id` が同じ行を1つのグループにまとめる」という意味です。グループごとに `COUNT(*)` を数えるので、「配信元ごとの記事数」になります。

ここで見てほしいのは、3行目の `source_id` が NULL のグループです。配信元が不明の記事5も、「NULL のグループ」として1行にまとまって出てきます。

| source_id | article_count | 意味 |
|---:|---:|---|
| 1 | 2 | テック日報の記事 |
| 2 | 2 | 経済ウィークリーの記事 |
| NULL | 1 | 配信元が不明の記事 |
| **合計** | **5** | **articles の全件数と一致する** |

> 🔍 **グループの合計は、元の件数と一致するはず**：`GROUP BY` は行を分けるだけで、増やしも減らしもしません。だから `COUNT(*)` の合計は、`WHERE` で絞ったあとの件数と一致します。一致しないときは、`JOIN` で行が増えている（第7章）か、`WHERE` で行が減っているかのどちらかです。

## 5. DISTINCT：重複を消す

`DISTINCT` は、結果の中で同じ行を1つにまとめます。

```sql
SELECT DISTINCT source_id
FROM articles
ORDER BY source_id;
```

:::result 3
| source_id |
|---:|
| 1 |
| 2 |
| <span class="null">NULL</span> |
:::

記事は5本ありますが、`source_id` の値は 1・2・NULL の3種類なので、3行になります。

> 🧭 **DISTINCT を見たら、なぜ重複したのかを疑う**：「使われている配信元の一覧」のように、もともと重複を消したいときに使うのは正しい使い方です。一方で、結果に同じ行が何度も出てきたのを `DISTINCT` で消している場合は、重複が生まれた原因（多くは、頼んでいない表の結合）が残ったままです。第7章で、この形の失敗を詳しく見ます。

## 6. ORDER BY と LIMIT：順番は書かないと決まらない

### 「新しい順に3件」の落とし穴

「公開日時が新しい順に3件」を、素直に書くと次のようになります。

```sql
SELECT id, title, published_at
FROM articles
ORDER BY published_at DESC
LIMIT 3;
```

:::result 3 wrong
| id | title | published_at |
|---:|---|---|
| 4 | 為替相場、週明けは小動き | <span class="null">NULL</span> |
| 5 | 配信元不明の転載記事 | 2026-10-03 18:00:00+09 |
| 3 | 半導体工場の新設計画を発表 | 2026-10-02 12:00:00+09 |
:::

公開日時が分からない記事4が、いちばん上に来ました。エラーは出ていません。

> 🔍 **なぜ NULL が先頭に来るのか**：PostgreSQL は、並べ替えのとき NULL を「どんな値よりも大きい」ものとして扱います。`DESC`（大きい順）にすると、NULL がいちばん先に並びます。

NULL を最後に回すには、`NULLS LAST` を付けます。

```sql
SELECT id, title, published_at
FROM articles
ORDER BY published_at DESC NULLS LAST
LIMIT 3;
```

:::result 3
| id | title | published_at |
|---:|---|---|
| 5 | 配信元不明の転載記事 | 2026-10-03 18:00:00+09 |
| 3 | 半導体工場の新設計画を発表 | 2026-10-02 12:00:00+09 |
| 2 | 社内AIの導入率が過半数に | 2026-10-02 08:30:00+09 |
:::

### 同じ値が並ぶと、どちらが先かは決まらない

`ORDER BY source_id LIMIT 1` のように、並べる列に同じ値（記事1と記事2はどちらも `source_id` が 1）があると、どちらが先に出るかは決まっていません。今日は記事1が出ても、データが増えたり、PostgreSQL の内部の都合が変わったりすると、記事2が出ることがあります。`ORDER BY` が無い `LIMIT` も同じで、どの行が出るかは決まっていません。

> 🧭 **順番を決めきる書き方**：最後に主キーを足して `ORDER BY source_id, id` のように書くと、同じ値のときの順番も決まります。主キーは重複しないので、順番が必ず1通りになります。

並び順は、文字の並べ方のルール（第3章で確かめた `lc_collate`）にも左右されます。メンバー間で設定が違うと、同じ SQL でも順番が変わることがあります。

## 7. ズレの3分類

ここまでの例は、どれもエラーにならずに結果がずれるものでした。この資料では、こうしたズレを3つに分けて呼びます。以降の章の「起きがちな失敗」も、この分け方で説明します。

| 分類 | 何が起きるか | この章の例 | 以降の章の例 |
|---|---|---|---|
| **行が減る** | あるはずの行が、結果から消える | `WHERE` で公開日時が NULL の記事が消える | INNER JOIN で相手のいない行が消える（第7章） |
| **行が増える** | 1行のはずのものが、何行にもなる | （この章には無い） | 1対多の JOIN で記事数が2倍になる（第7章） |
| **値が変わる** | 行数は合っているのに、値や順番が違う | `COUNT(*)` と `COUNT(列)` の違い、NULL が先頭に来る並び順 | タイムゾーン（第5章）、型による比べ方（第5章） |

> 🧭 **なぜ分類するのか**：「なんか数字が変」のままだと、どこを疑えばよいか決まりません。「行が減った」なら `WHERE` と INNER JOIN、「行が増えた」なら JOIN、「値が変わった」なら `COUNT` の中身や型、タイムゾーンを疑う、というように、分類が決まると疑う場所が決まります。

## 8. 検算の4手順

ズレに気づくための手順です。この資料では、毎回この順番で確かめます。

| 手順 | やること | 第4章の検証材料 | この章の例（配信元ごとの記事数） |
|---|---|---|---|
| ① | 基準の表の件数を数える | a | articles は 5 |
| ② | 処理後の件数（合計）を数える | b | 2＋2＋1＝5 |
| ③ | 差の理由を言葉で説明する | b（理由） | 差は 0。GROUP BY は行を分けるだけなので正しい |
| ④ | 期待していた件数と比べる | あなた | 「配信元が不明な記事も1行で出す」と頼んだなら 5 で正しい |

①と②は、Claude Code に出させれば済みます（検証材料 a・b）。③も Claude Code に書かせますが、その説明が正しいかは、あなたが読んで判断します。④は、何を頼んだかを知っているあなたにしかできません。

> 🧭 **③で説明できない結果は使わない**：①と②の差を言葉で説明できないときは、どこかで想定外のことが起きています。結果が「それらしい数字」でも、使わずに頼み直すか、資料作成者に質問してください。

## 9. 第2〜4章の SQL を読み直す

第2〜4章で「写して実行する SQL」として使った SQL も、いまなら読めます。

```sql copy=6
SELECT
    (SELECT COUNT(*) FROM sources)      AS sources,
    (SELECT COUNT(*) FROM articles)     AS articles,
    (SELECT COUNT(*) FROM tags)         AS tags,
    (SELECT COUNT(*) FROM article_tags) AS article_tags;
```

:::result 1
| sources | articles | tags | article_tags |
|---:|---:|---:|---:|
| 3 | 5 | 4 | 8 |
:::

第3章で「最初の状態」を確かめた SQL です。`( )` の中にそれぞれ小さな SELECT があり、4つの表の `COUNT(*)` を1行に並べています。`FROM` が無いのは、どの表の行でもなく、計算した値を1行だけ出すためです。

第4章でロールを確かめた SQL は、「`pg_roles`（ロールの一覧の表）から、`WHERE rolname IN (...)` で3つのロールの行だけ残し、`ORDER BY rolname` で名前順に並べる」と読めます。

**この章で足す検証材料**

| 記号 | 足すもの | 理由 |
|---|---|---|
| b | グループごとの数の合計と、基準の件数（a）の比較 | GROUP BY は行を増やしも減らしもしないので、合計は一致するはず |

| e | どの `COUNT` を使ったか、`ORDER BY` で順番を決めきったか | 同じ「件数」「上位3件」でも、書き方で答えが変わる |

**出てきたものの検証ポイント**

1. 結果の合計が、a（articles の総件数）と一致しているか
2. `COUNT(...)` の中身が、頼んだ意味と合っているか
3. `LIMIT` があるなら、その前に `ORDER BY` があり、主キーなどで順番が決めきられているか

**起きがちな失敗と、その理由**

- **「最新の3件」に、公開日時が不明な記事が入る**：`DESC` で並べると NULL が先頭に来るためです。（値が変わる）
- **「記事数」が 4 と報告される**：`COUNT(published_at)` や `COUNT(source_id)` で数えると、NULL の行が数えられないためです。どの列の NULL でない数なのかを、e で確かめます。（値が変わる）
- **`DISTINCT` を付けて「重複を除きました」と報告される**：重複が出た原因が残っているかもしれません。どの表を `FROM` や `JOIN` に入れたかを読みます。（行が増える、の隠れた形）
- **実行するたびに、結果の順番が変わる**：`ORDER BY` が無いか、同じ値の行の順番が決まっていないためです。（値が変わる）
:::

## 確認問題

:::quiz Q1. Claude Code が「記事は 4 件です」と報告しました。SQL は `SELECT COUNT(source_id) FROM articles;` でした。あなたの psql では `COUNT(*)` が 5 です。どこを疑いますか？
`COUNT(source_id)` を疑います。これは「`source_id` が NULL でない行の数」なので、配信元が不明な記事5を数えていません。「記事の件数」を知りたいなら `COUNT(*)` です。ズレの3分類では「値が変わる」にあたります。
:::

:::quiz Q2. 「配信元ごとの記事数」の結果が「1：2件、2：2件」の2行で、合計は 4 でした。articles の総件数は 5 です。検算の4手順の③で、差の 1 をどう説明しますか？ また、それで正しいかはどう決めますか？
差の 1 は、`source_id` が NULL の記事5です。`WHERE source_id IS NOT NULL` や INNER JOIN などで消えた（行が減る）と説明できます。それで正しいかは④で決まります。「配信元が分かる記事だけ」を頼んだなら 4 で正しく、「全記事を配信元ごとに」を頼んだなら、NULL のグループが抜けているので誤りです。
:::

:::quiz Q3. 「新しい順に3件」と頼んだら、1件目が「為替相場、週明けは小動き」でした。公開日時の欄は空です。どこを疑いますか？
`ORDER BY published_at DESC` で、NULL が先頭に来ていることを疑います。公開日時が分からない記事は、「新しい記事」とは言えません。`NULLS LAST` を付けるか、`WHERE published_at IS NOT NULL` で除くように頼み直します。どちらにするかは、「公開日時が不明な記事を一覧に入れたいか」で決めます。
:::

:::why 📚 なぜ？豆知識（読み飛ばしてもかまいません）

### 🔍 書く順と考える順が違う理由

SQL は、英語の文に近い「何を（SELECT）、どこから（FROM）、どんな条件で（WHERE）」という順番で書くようになっています。書く順番は人にとっての読みやすさに合わせたもので、PostgreSQL が考える順番とは違っています。`SELECT` で付けた別名（`AS article_count` など）を `WHERE` で使えないのも、`WHERE` が `SELECT` より先に考えられるからです。

### 🔍 NULL の並び順を決める

`NULLS FIRST`（NULL を先頭）と `NULLS LAST`（NULL を最後）で、NULL の位置を指定できます。何も書かないと、小さい順（`ASC`）では最後、大きい順（`DESC`）では先頭になります。

### 🧭 `SELECT *` をあまり使わない理由

`SELECT *` は「すべての列」の意味です。手早く中身を見るには便利ですが、表に列が増えると結果も変わります。Claude Code に結果を出させるときは、必要な列を名前で書かせたほうが、何を見ているかがはっきりします。

さらに知りたい人は、公式ドキュメント（PostgreSQL 18）の [問い合わせ（SELECT）](https://www.postgresql.org/docs/18/queries.html) と [集約関数](https://www.postgresql.org/docs/18/functions-aggregate.html) を参照してください。
:::
